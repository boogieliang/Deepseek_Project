# 从原型到系统：农资 CEO 驾驶舱升级方案

> 面向对象：决策者 + 将要执行的技术团队
> 配套可运行示例：[system/README.md](system/README.md)（Python 一行命令启动，真实读写数据库）

---

## 0. 先给结论

现在这版 HTML 是一个**高质量的"渲染层"**：布局、指标、图表、文案都对了，但数据写在 JS 里，刷新即还原，改不了、存不下、算不准。

要变成"每周喂数据、系统自己算、所有模块实时更新、还能给建议"的系统，本质只差四件事：

| # | 缺什么 | 补什么 | 难度 |
|---|---|---|---|
| 1 | **没有存储** | 数据库 + 主数据 + 事实表 | 中 |
| 2 | **没有写入** | 填报表单 / Excel 导入 / 接口对接 + 校验 | 中 |
| 3 | **没有计算** | 服务端指标层（口径唯一）+ 增量重算 | 中高 |
| 4 | **没有权限与留痕** | 角色、审批、审计日志 | 中 |

再加两件"锦上添花但决定成败"的事：

| # | 缺什么 | 补什么 |
|---|---|---|
| 5 | **建议是写死的文案** | 可配置规则引擎 + 归因模型 → 真建议 |
| 6 | **只有"看"没有"干"** | 预警派单、责任人、闭环率 |

**我已经把 1-3 和 5 的最小闭环跑通了**（见 `system/`，420 条真实入库数据，改一条记录全站重算）。剩下的是把这套东西"生产化 + 铺满模块"。

## 1. 现状体检：原型 vs 系统

| 能力 | 现在的原型 | 系统的要求 | 差距 |
|---|---|---|---|
| 数据来源 | `buildData()` 伪随机生成 | 数据库 + 外部接口 | 全部重写 |
| 数据写入 | 无 | 表单 / 导入 / API | 从 0 到 1 |
| 计算位置 | 浏览器（每个 tab 算一次） | 服务端指标层，口径唯一 | 迁移 |
| 数据更新 | 刷新即还原 | 实时 / 定时增量 | 调度 |
| 建议 | 硬编码在 HTML 里 | 规则 + 模型，可解释可跟踪 | 重构 |
| 权限 | 无（谁打开都一样） | 角色 + 行级数据权限 | 从 0 到 1 |
| 审计 | 无 | 谁改了什么、何时改 | 从 0 到 1 |
| 部署 | 双击一个文件 | 服务 + 备份 + 监控 | 从 0 到 1 |
| 多端 | 只有桌面浏览器 | PC + 企微/小程序 | 二期 |

一句话：**原型的价值是"需求已被验证"，它现在是 UI 规格说明书和验收基准，不是系统的地基。**

## 2. 目标架构（五层）

```
┌──────────────────────────────────────────────────────────────┐
│  ① 接入层  周报表单 · Excel 导入 · 经销商 APP · ERP 抽取 · 行情 API │
└───────────────────────────┬──────────────────────────────────┘
                            ↓ 校验 / 幂等 / 审批 / 审计
┌──────────────────────────────────────────────────────────────┐
│  ② 存储层  PostgreSQL（业务） + 对象存储（附件） + Redis（缓存）    │
│     主数据：大区/品类/作物/客户/经销商/产品/组织                    │
│     事实数据：周度销量、回款、库存批次、服务记录                     │
└───────────────────────────┬──────────────────────────────────┘
                            ↓ 增量重算（每周/每日）
┌──────────────────────────────────────────────────────────────┐
│  ③ 指标层  指标字典 → DWD 明细 → DWS 汇总 → KPI 物化表            │
│     收入 / 毛利率 / 回款率 / 周转 / 达成率 / 临期率 / 健康分        │
└───────────────────────────┬──────────────────────────────────┘
                            ↓
┌──────────────────────────────────────────────────────────────┐
│  ④ 智能层  规则引擎（阈值/同比/组合）→ 统计模型（预测/异常）→ LLM   │
│     输出：事实 + 归因 + 动作 + 影响金额 + 责任人 + 时限            │
└───────────────────────────┬──────────────────────────────────┘
                            ↓
┌──────────────────────────────────────────────────────────────┐
│  ⑤ 应用层  PC 驾驶舱 · 移动端 · 预警中心 · 任务闭环 · 导出/汇报     │
└──────────────────────────────────────────────────────────────┘
```

**关键原则**：④ 只能读 ③ 的数字，绝不能自己算；⑤ 只能调 ④ 的接口，不能内嵌业务规则。否则三个月后又是三套数。

## 3. 数据模型：先建这 9 张表

MVP 只做了 1 张事实表，真实系统至少要这些：

### 3.1 主数据（变化慢，先建）

| 表 | 关键字段 | 作用 |
|---|---|---|
| `dim_region` | id, name, parent_id, manager_id | 大区/省/县树，支持行级权限 |
| `dim_category` | id, name, level, parent_id | 品类树（复合肥→硫基/氯基） |
| `dim_crop` | id, name, region_ids | 作物带，用于"作物×品类"矩阵 |
| `dim_product` | id, sku, name, category_id, spec, shelf_life_days | 效期计算的基准 |
| `dim_customer` | id, name, type(经销商/大户/合作社), region_id, credit_limit | 信用与画像 |
| `dim_dealer` | 同 customer 或子表 | 经销商进销存归属 |

### 3.2 事实数据（按周/按日追加）

```sql
-- 周度销售事实（最核心，粒度：周 × 大区 × 品类 × 客户）
CREATE TABLE fact_weekly_sales (
  id            BIGSERIAL PRIMARY KEY,
  week          VARCHAR(8)  NOT NULL,        -- 2026-W44
  region_id     INT REFERENCES dim_region(id),
  category_id   INT REFERENCES dim_category(id),
  customer_id   INT REFERENCES dim_customer(id),
  qty           NUMERIC(14,3),               -- 吨/箱/袋
  amount        NUMERIC(14,2),               -- 含税收入（元）
  cost          NUMERIC(14,2),               -- 成本（含运费）
  target        NUMERIC(14,2),
  source        VARCHAR(16) DEFAULT 'manual',-- manual/import/erp
  created_by    INT, created_at TIMESTAMP, updated_at TIMESTAMP,
  UNIQUE(week, region_id, category_id, customer_id)   -- 幂等键
);

-- 回款与应收（粒度：周 × 客户）
CREATE TABLE fact_receivable (
  id BIGSERIAL PRIMARY KEY, week VARCHAR(8), customer_id INT,
  opening NUMERIC(14,2), billed NUMERIC(14,2), collected NUMERIC(14,2),
  closing NUMERIC(14,2), overdue_days INT
);

-- 库存批次（粒度：批次 × 仓）
CREATE TABLE fact_inventory_batch (
  id BIGSERIAL PRIMARY KEY, batch_no VARCHAR(32), product_id INT, warehouse_id INT,
  qty NUMERIC(14,3), cost NUMERIC(14,2),
  production_date DATE, expire_date DATE, snapshot_date DATE
);

-- 农技服务（粒度：场次）
CREATE TABLE fact_service (
  id BIGSERIAL PRIMARY KEY, service_date DATE, region_id INT, customer_id INT,
  type VARCHAR(16),  -- 观摩会/测土/回访/示范田
  staff_id INT, attendee_cnt INT, cost NUMERIC(10,2)
);
```

### 3.3 派生与治理

| 表 | 作用 |
|---|---|
| `kpi_weekly_snapshot` | 按「周 × 大区 × 品类」预聚合的指标，前端只读它（毫秒级响应） |
| `alert` | 预警实例：规则id、对象、级别、影响金额、状态 |
| `action_task` | 派单：责任人、截止日、处理结果 → 闭环率 |
| `metric_dict` | 指标字典：名称、公式、口径、更新频率、责任人（**最重要的表**） |
| `audit_log` | 谁在何时改了哪条数据（字段级 diff） |

> **经验值**：这类系统的失败 70% 死在 `metric_dict` 没定清楚——销售、财务、供应链各算一套收入，第一次高管会就吵翻。

## 4. 每周数据怎么进系统（这是成败关键）

### 4.1 三条通路

| 通路 | 场景 | 实现 | 工期 |
|---|---|---|---|
| **A. 手工填报** | 业务员/财务报周度情况 | 移动端表单（企微/小程序），草稿、暂存、提交 | 1.5 周 |
| **B. Excel 导入** | 财务从 ERP 导表 | 模板下载 → 上传 → 校验预览 → 确认入库 | 1 周 |
| **C. 接口对接** | ERP/进销存/经销商 APP | 定时抽取（CDC 或 API），T+1 | 2-3 周 |

### 4.2 一个反直觉但极其重要的设计

> **不要让业务员重复录入 ERP 里已经有的数据。**

老板想象的"每周把所有信息传给系统"如果照做，业务员一周要填 40 个字段，三个月后数据必然失真（填假数、漏填、拖延）。

正确做法：**系统能自动拿的一律自动，只让人填"系统拿不到、但决定判断"的 5 个字段**：

1. **渠道库存天数**（经销商仓库里的货还能卖多久）
2. **终端动销率**（零售店实际卖给农户的速度）
3. **临期/滞销金额**（需不需要调拨或促销）
4. **竞品价格动作**（本周谁降价、降多少）
5. **农事进度**（当地播种/施肥/打药到哪一步了）

其余（收入、成本、回款、订单、库存数量）全部从 ERP / 银行流水 / WMS 自动取。
**填报时间控制在 3 分钟以内**，数据质量才保得住。

### 4.3 校验规则（不做这个，后面全是脏数据）

| 规则 | 说明 |
|---|---|
| 必填与值域 | 收入 ≥ 0；回款率 0-100；周转 0-365 |
| 勾稽 | 本期回款 ≤ 应收余额；期末库存 = 期初 + 入库 − 出库 |
| 突变检测 | 单周环比 ±50% 必须填原因，否则拦截 |
| 重复提交 | `(周次, 大区, 品类)` 唯一键，幂等覆盖（MVP 已实现） |
| 权限校验 | 只能填自己负责的大区 |
| 审批 | 提交 → 大区经理 → 财务复核 → 生效（生效后才进指标） |

### 4.4 更新时机

- 手工/导入：**提交即算**（触发该周该大区的增量重算，1-3 秒）
- ERP 对接：**T+1 凌晨批处理**，早上 8 点前刷新
- 外部行情：15 分钟一次
- 前端：页面打开拉一次 + 每 5 分钟轮询（或 SSE 推送），保证"看到的就是最新"

## 5. 指标层：怎么做到"所有模块实时更新且口径一致"

### 5.1 分层

```
ODS（原始） → DWD（清洗/关联主数据） → DWS（周×大区×品类 宽表） → KPI（指标表）
```

前端**只读 KPI 表**，不碰明细。数据量再大，一次查询也是毫秒级。

### 5.2 增量重算

不要每次全量重算 3 年数据。做法：

1. 写入时记录 `dirty_key = (week, region)` 到队列表
2. 后台任务消费：只重算这些 key 的 DWS + KPI
3. 更新 `kpi_weekly_snapshot` 并失效 Redis 缓存
4. 前端轮询发现 `version` 变化就刷新

### 5.3 实时性分级（不要什么都追求实时）

| 数据 | 频率 | 理由 |
|---|---|---|
| 订单、库存 | 5 分钟 | 影响发货决策 |
| 回款、应收 | T+1 | 银行流水日终 |
| 财务口径毛利 | 月结 | 成本核算周期 |
| 行情价格 | 15 分钟 | 采购窗口 |

## 6. 建议引擎：从"写死的文案"到"真建议"

### 6.1 三级火箭

| 级别 | 技术 | 输出 | 举例 |
|---|---|---|---|
| L1 规则 | 阈值 + 同比 + 组合 | "回款率 83.4% < 88%，敞口 676 万" | 现在就有 |
| L2 统计 | 同环比、季节分解、异常检测 | "西北本周收入较季节均值低 18%，主因复合肥" | 二期 |
| L3 归因/话术 | LLM（输入只能是 L1/L2 的结构化结果） | "建议本周对西北停发复合肥，改推特肥" | 三期 |

### 6.2 每条建议必须满足 5 个条件

1. **可解释**：引用具体数字和对比基准（"83.4% vs 红线 88%"）
2. **可执行**：动词开头，明确对象（"对西北 3 家超账期客户停货"）
3. **可度量**：影响金额（"敞口 676 万"）
4. **可跟踪**：责任人 + 截止日 + 状态
5. **不重复**：同一问题 7 天内不重复推送，除非恶化

### 6.3 反"建议疲劳"设计

- 每天最多推 **5 条**，按影响金额排序
- 分三级：P0（今天就动）、P1（本周）、P2（本月优化）
- "已处理"要能一键标记，否则第二周就没人看
- 建议的采纳率、闭环率要作为系统本身的 KPI 展示

### 6.4 LLM 的正确用法

| ✅ 该做 | ❌ 不该做 |
|---|---|
| 把 5 条指标变化写成一段人话 | 让模型自己算收入/毛利 |
| 给出 2-3 个归因假设，让人判断 | 让模型直接下结论并自动执行 |
| 生成周报、会议纪要、经销商沟通话术 | 把明细数据丢进 prompt 让它"分析" |

**铁律：数字来自指标层，模型只负责翻译和假设。**

## 7. 交互与权限：从"看"到"改"

### 7.1 角色矩阵

| 角色 | 看 | 填 | 审批 | 改主数据 | 导出 |
|---|---|---|---|---|---|
| CEO / 董事长 | 全部 | — | — | — | ✅ |
| 大区总经理 | 本大区 | ✅ | ✅ 本区 | — | ✅ |
| 业务员 | 本人客户 | ✅ | — | — | 部分 |
| 财务 | 全部（金额） | ✅ 回款 | ✅ | 客户信用 | ✅ |
| 供应链 | 全部（库存） | ✅ 库存 | — | 产品/仓库 | ✅ |
| 管理员 | 全部 | — | — | ✅ | ✅ |

行级权限用 `region_id` 做数据过滤，不要靠前端隐藏。

### 7.2 从"只读"升级到"可操作"的交互清单

- **下钻**：大区 → 省 → 客户 → 单据，最多 3 层
- **筛选**：时间、大区、品类、客户类型，状态保存在 URL 里可分享
- **编辑**：仅本人/本区、仅本期、必须填修改原因
- **批注**：在某条指标下 @人 讨论（比截图发微信强）
- **派单**：预警一键生成任务，推到企微
- **导出**：Excel / PPT 汇报版（CEO 每月要交的东西）

## 8. 技术选型（三套，按预算选）

| 方案 | 组成 | 周期 | 成本 | 适合 |

## 11. 六个必踩的坑（提前避开）

1. **指标口径打架** —— 先出 `metric_dict` 并让财务签字，再写代码。
2. **填报负担过重** —— 只填 5 个系统拿不到的字段，其余自动。
3. **追求"实时"** —— 财务数据做不到实时，硬做只会得到错的实时数。
4. **建议不可执行** —— "毛利率下降"不是建议，"对 XX 客户停货并调价 2%"才是。
5. **权限做太粗** —— 大区总能看到隔壁大区的客户，第一个月就会出事。
6. **一步上 AI** —— 没有干净主数据和标签，模型只会放大错误。

## 12. 这一版已经验证了什么

`system/` 里跑通的部分，可以直接作为 P1 的验收基准：

- ✅ 写入：表单 / API → SQLite，幂等 + 审计
- ✅ 计算：6 个指标 + 周序列 + 品类/大区聚合
- ✅ 更新：保存后 1 秒内全站重算
- ✅ 建议：7 条规则，输出级别/事实/动作/影响金额
- ✅ 交互：筛选、编辑、删除、新增、抽屉表单、Toast
- ✅ 可解释：每条建议都能点开看到触发它的数字
